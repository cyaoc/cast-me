# Edit-Chain Depth as an Identity Constraint

## Problem Statement

Repeatedly revising the same generated image makes it visibly dirty. Scatter points appear, a green cast creeps in, texture flattens, and instruction-following degrades. Users see this firsthand after several rounds of changes.

The cause is mechanical and has been isolated. Editing requires encoding an image into a latent representation and decoding it back to pixels, and that round trip is lossy. A published experiment removed the edit instruction entirely and asked only for an exact copy, repeatedly; the noise accumulated anyway. Degradation therefore tracks how many times a result has been fed back in as an image input, not what was changed. Depth of the edit chain is the only variable that reliably controls it.

Three findings make this worse than an ordinary quality issue. Explicit cleanup instructions do not work — a replication study found that prompting for denoising at every step produced the same green cast and texture loss as not prompting at all, while the model's own reasoning summary claimed the denoising had been performed. Neither the model nor general image-quality metrics can detect the problem: twenty-one of twenty-three no-reference quality metrics scored degraded images higher, and models first mentioned noise many steps after a human would have seen it. And a model cannot recover by referring to a cleaner image earlier in the conversation, so a prompt instructing it to match the earlier version does not work; only actually changing the image inputs does.

The detail that degrades first is the detail that carries identity. The same study documented a simplification bias in which fine, high-frequency features were collapsed by the second step. Moles, scars, freckles, and under-eye shadows are exactly that kind of feature, and they are the channels recognition falls back on when other cues weaken.

CastMe already limits this by accident. It permits at most one automatic correction, it regenerates from the Primary Identity Anchor when identity-wide drift occurs, and it excludes the failed result from that regeneration's inputs. Each of those rules exists for an identity reason, and each happens to keep the chain short.

The remaining gap is narrow but real. The recovery table offers a surgical edit that passes the result being edited back in as an image input, and the single automatic correction is permitted to choose that row on its own initiative. That is the one place the skill can lengthen the chain without the user asking for it, and it chooses without distinguishing a result it has just produced from the person's photograph from a result that is itself the product of earlier edits.

That distinction has to be answerable without bookkeeping. CastMe is an instruction-only Skill with no storage, and this repository has already settled the question of implicit conversation state: refresh history is compared only against what remains available in the current conversation, no stronger guarantee is promised, and no scratchpad, hook, service, file, or database may be added to simulate one. The coordinating workflow separately forbids maintaining a read-state tracker. A running count of how many times an image has been through the model would be exactly the bookkeeping those rules reject.

## Solution

Make regeneration from the Primary Identity Anchor the default recovery and the surgical edit the exception, reversing the current framing without removing either path. A surgical edit remains the right operation for one coherent local defect on an otherwise correct result, because regenerating discards everything that was already right; it is not the right operation on a result that is already the product of an earlier edit.

Restrict the single automatic correction accordingly. The skill may automatically edit only a **freshly generated result**: one it produced in the current exchange, can still see, and produced with no image input that was itself a generated image. In every other failing case the automatic correction regenerates from the request's fixed root and the locked brief. The fixed root is the set of image inputs every generation for the request starts from and which does not grow with each round: the Primary Identity Anchor, any required reliable supporting person reference, and any locked produced artifact that every image in the request is built from. This narrows exactly one degree of freedom in the existing recovery contract and changes nothing else about it.

Answer the freshness question from the immediate exchange rather than from a count. The ordinary case is trivial — the skill generated the image a moment ago and knows what it passed in — and no history needs to be traversed to answer it. When the skill cannot tell, it regenerates. Uncertainty therefore routes to the path that restarts the chain rather than the one that lengthens it, so a long conversation degrades the recommendation instead of silently degrading the image.

Never repair a locked produced artifact by editing it, even when that artifact is itself freshly generated. Regenerate it instead. An ordinary result is terminal — nothing is built from it, so one edit costs one image. An artifact that later images reuse as an image input is not terminal, and editing it puts every image derived from it one step further along the chain, so the cost of that single edit is multiplied by every image the request produces.

When a user keeps requesting changes to a result that is not freshly generated, recommend regenerating from the request's fixed root with every accumulated lock carried forward, while leaving the direct edit available.

Do not add a visual dirtiness check. Degradation is precisely the failure that neither the model nor generic quality metrics can see, so a review item asking the model to judge whether an image looks noisy would produce a confident and unreliable verdict. Manage it structurally through chain depth instead, and never claim that noise was removed.

## User Stories

1. As a user who has asked for several rounds of changes, I want the skill to stop feeding each result into the next revision, so that my image does not accumulate scatter points, a green cast, and flattened texture.
2. As a user who wants to keep iterating, I want later rounds to start again from my original photo with all my locked choices carried forward, so that continued work does not mean continued degradation.
3. As a user asking for one small named fix on an otherwise correct first result, I still want a surgical edit, so that a proportionate repair does not discard the composition, styling, and scene that were already right.
4. As a user asking for a change to a result that is already the product of an earlier edit, I want regeneration from my original photo recommended, so that the chain restarts instead of growing.
5. As a user in that situation, I still want the direct edit available if I ask for it, so that the recommendation does not become a restriction.
6. As a user whose result fails Identity Review with identity-wide drift, I want regeneration from my original photo, so that the failed face is not the raw material for its own repair.
7. As a user receiving the one automatic correction, I want it to regenerate rather than edit whenever the failing result was not just produced from my photograph, so that the skill never lengthens the chain on its own initiative.
8. As a user, I do not want more than one automatic correction, so that recovery stays bounded.
9. As a user with a mole, scar, freckles, or an under-eye shadow, I want those details to survive revision, so that the features that make me recognizable are not quietly simplified away.
10. As a user, I do not want the skill to add a judgment about whether my image looks noisy, so that it does not report a verdict it cannot reliably make.
11. As a user, I do not want the skill to claim it removed noise or improved image cleanliness, so that its completion claims stay truthful.
12. As a user, I do not want an instruction such as remove the noise, enhance the quality, or make it sharper used as a repair, so that a vague cleanup does not add over-sharpening and contrast that make artifacts more obvious.
13. As a user, I want recovery to actually change the image inputs rather than instructing the model to refer to an earlier, cleaner image, so that the recovery does something the model can actually act on.
14. As a user, I want my original photo to remain the source for every regeneration, so that each regeneration is a fresh branch rather than a longer chain.
15. As a user, I want every resolved scene, shot, camera, pose, styling, lighting, finish, text, background, and accepted-risk choice carried into a regeneration, so that restarting the chain does not restart the conversation.
16. As a user whose first result passes review, I do not want a routine second pass, so that this feature adds no generation cost to work that already succeeded.
17. As a user asking for a series or several related images, I want each one generated from my original photo rather than derived from the previous image, so that later images in the set are not dirtier than the first.
18. As a user, I do not want the skill to promise a specific number of safe edits, so that it does not state a threshold it has no evidence for.
19. As a user in a long conversation where the skill can no longer tell how the current image was made, I want it to regenerate from my photograph rather than guess, so that losing track degrades the recommendation instead of degrading my image.
20. As a user on a generation surface that cannot exclude the failed result from the inputs, I want the skill to ask me to reattach my original photo rather than silently editing the failed result, so that a surface limitation does not become a hidden chain extension.
21. As a user whose result has multiple connected body-scale failures, I want the existing regeneration recovery preserved, so that this change does not disturb a path that already avoids the chain.
22. As a user whose result was produced using another generated image as one of its inputs, I want a failing result regenerated rather than edited, so that the repair does not stack a second round trip onto one the image already carries.
23. As a user, I want a regeneration to carry every fixed input my request depends on rather than my photograph alone, so that restarting the chain does not hand me something that is no longer what I asked for.
24. As a user whose images are all built from one locked artifact, I want that artifact regenerated rather than edited when it fails, so that a single repair to it is not inherited by every image in the set.
25. As a beginner, I want all of this handled internally, so that I never have to think about how image editing degrades.
26. As a maintainer, I want this to narrow exactly one degree of freedom in the existing recovery contract, so that the change is small enough to review and reverse.
27. As a maintainer, I want no numeric depth threshold anywhere in the implementation, because the quantitative findings come from other models and the study deliberately excluded photorealistic faces.
28. As a maintainer, I want no image-quality metric, no-reference scorer, or noise detector added, because the published metric comparison shows most of them score degraded images higher.
29. As a maintainer, I want the existing bounded single automatic correction preserved rather than relaxed, now supported by a mechanical rationale in addition to its original one.
30. As a maintainer, I want scenarios that assert routing and actual image inputs rather than image appearance, so that the tests do not depend on inspecting generated pixels.
31. As a maintainer, I want no counter, ledger, or scratchpad introduced for this, so that the skill remains instruction-only and consistent with the repository's existing refusal to simulate conversation state.
32. As a maintainer, I want the freshness question answerable from the immediate exchange, so that the rule does not quietly depend on history that may not be available.
33. As a maintainer, I want the freshly-generated test stated as a property of an operation's image inputs rather than as a phrase about the anchor, so that it cannot be read as satisfied merely because the Primary Identity Anchor appears in the input list.
34. As a maintainer, I want edit-chain depth kept as an internal concept rather than a new capitalized domain term, so that this change needs no glossary entry or ADR.

## Implementation Decisions

- Deepen the existing Identity Anchor recovery rules and the existing review step. Do not add a module, agent, workflow stage, gate, or runtime component.
- Reverse the default framing of the existing recovery table. Regeneration from the Primary Identity Anchor is the default path; the surgical edit is the proportionate exception for one coherent local defect on a freshly generated result.
- Define a freshly generated result as one the skill produced in the current exchange, can still see, and produced with no image input that was itself a generated image. State the test as a property of the operation's image inputs rather than as a phrase about the anchor. A membership reading, under which the Primary Identity Anchor merely appearing among the inputs is enough, leaves the rule with nothing to constrain: the surgical edit row passes the Primary Identity Anchor alongside the result being edited, so the product of an edit would satisfy it and could be edited again without limit. This remains a property of the immediate exchange, not a fact retrieved from conversation history.
- Define the request's fixed root as the image inputs every generation for that request starts from and which does not grow with each round: the Primary Identity Anchor, any required reliable supporting person reference, and any locked produced artifact that every image in the request is built from. Regeneration carries the fixed root, not the Primary Identity Anchor alone.
- Restate the identity-wide regeneration row so its inputs are the request's fixed root rather than the Primary Identity Anchor plus only required reliable supporting person references. The current wording is exclusive and would drop a locked produced artifact the request needs in every generation, silently returning a two-stage request to the single-stage behavior it was designed to replace. The failed result stays excluded.
- Never repair a locked produced artifact by editing it, even when it is itself freshly generated. Regenerate it. An ordinary result is terminal and one edit costs one image; an artifact that later images reuse as an image input is not terminal, so editing it puts every derived image one step further along the chain and multiplies the cost of that edit by every image the request produces.
- Restrict the single automatic correction to the surgical row only when the failing result is freshly generated and the defect is one coherent local unit. Otherwise the automatic correction must regenerate. Leave every other condition on that correction unchanged, including the requirement for a visible, inspectable result and verified surface controls.
- Justify that restriction by simplification bias rather than by a noise threshold. Fine high-frequency detail was documented collapsing by the second replication step, and those details are the recognition channels that matter most.
- Do not introduce a counter, ledger, scratchpad, or any other record of how many times an image has been through the model. The repository has already rejected simulated conversation state for refresh history and forbids a read-state tracker in the coordinating workflow; the same reasoning applies here, and the freshness test is designed so that no such record is needed.
- Regenerate whenever the skill cannot establish that a result is freshly generated. The default under uncertainty must be the path that restarts the chain, so that lost context costs a discarded good result at worst rather than a silently degraded one.
- When a user requests further changes to a result that is not freshly generated, recommend regeneration from the request's fixed root carrying every accumulated lock, and keep the direct edit available. This is a recommendation, not a gate. A user-requested edit keeps the existing surgical inputs of the result being edited plus the Primary Identity Anchor; do not add the request's locked produced artifact to them, since its design is already present in the image being edited and adding it would only deepen the operation's inputs.
- Do not add any review item that asks whether an image looks noisy, dirty, degraded, or low quality. The evidence is explicit that both the model and generic quality metrics fail at this judgment.
- Do not use cleanup instructions as a repair mechanism. Explicit denoising instructions were shown ineffective, and vague quality-improvement wording produces over-sharpening and raised contrast that make artifacts more visible.
- Never claim that noise, artifacts, or degradation were removed. The model's own reports on this were shown to be both delayed and inaccurate.
- Require recovery to change the actual image inputs. Prompt text instructing the model to refer to an earlier, cleaner image in the conversation does not work and must not be used as a substitute.
- For a requested series or set of related images, derive each image from the request's fixed root and the locked brief rather than from the previously generated image. Look Continuity is preserved through the written brief, not through chaining.
- Preserve the existing Structural Scale Failure recovery, the existing unavailable-anchor reattachment behavior, and the existing rule that a passing first result receives no routine second pass.
- Keep edit-chain depth an internal concept and keep the freshly generated result an ordinary condition inside the recovery rules. Do not add a domain term or an ADR; this is a reversible narrowing of an existing contract.

## Testing Decisions

- Use `evals/golden-conversations.md` as the single behavioral seam, consistent with every prior specification in this repository.
- Assert routing decisions and the actual image inputs of each operation. Never assert anything about how a generated image looks, since the whole point is that appearance-based detection is unreliable.
- Update the Shared checks entries covering likeness-complaint routing and automatic identity-wide regeneration, so that they state the new default and the freshly-generated condition on automatic editing.
- Reuse `Coherent local identity defects stay surgical` as the control, reading both of its cases as freshly generated results. It must keep producing a surgical edit whose inputs are the result being edited plus the Primary Identity Anchor, proving this change is a narrowing rather than a ban.
- Add an already-edited-result scenario in which the user requests another change. Assert that regeneration from the Primary Identity Anchor is recommended, that every accumulated lock is carried into the new prompt, and that the direct edit remains available on request.
- Add an automatic-correction scenario on a result that is already the product of an earlier edit. Assert that the automatic path regenerates and that the failed result is excluded from the inputs.
- Add a scenario on a result produced from the Primary Identity Anchor together with a locked produced artifact. Assert that the automatic correction regenerates rather than edits, and that the regeneration carries the fixed root including that artifact rather than the Primary Identity Anchor alone.
- Add a control asserting that the Primary Identity Anchor appearing among an operation's image inputs does not by itself make that operation's output freshly generated.
- Add a scenario in which a locked produced artifact that later images reuse fails its own review. Assert that it is regenerated rather than edited, even though nothing else would disqualify it from the surgical row.
- Add a scenario in which the user explicitly requests an edit to a result produced from a locked produced artifact. Assert that regeneration is recommended, that the edit still proceeds on request, and that its inputs remain the result being edited plus the Primary Identity Anchor.
- Add an indeterminate-provenance scenario in which the conversation no longer shows how the current image was produced. Assert that the skill regenerates rather than edits, and that it does not claim to know the image's history.
- Add a multi-round scenario across at least three requested changes. Assert that no operation passes an image that was itself produced by an edit back in as an input without the user explicitly asking for that edit.
- Add a series scenario asserting that each image derives from the Primary Identity Anchor rather than from the previous output, with continuity carried by the brief.
- Add a scenario in which the user asks the skill to clean up or sharpen a dirty-looking result. Assert that the skill does not attempt a cleanup edit, does not claim noise removal, and offers regeneration from the Primary Identity Anchor instead.
- Add a scenario asserting that no review output contains a noise, dirtiness, or degradation verdict, and that no count, tally, or remaining-edits figure is shown to the user.
- Preserve `Identity-wide drift regenerates from reliable evidence`, `Automatic identity recovery is bounded and reviewed`, `Passing or unreviewable outputs receive no automatic pass`, `Surface-limited identity recovery does not pretend to regenerate`, and the existing Structural Scale Failure recovery unchanged. Each already avoids the chain, and none of them should shift.
- Verify by inspection that no numeric depth threshold appears anywhere in the implementation or the scenarios.
- Run the existing structural skill validator afterwards as a packaging and reference-integrity check.

## Out of Scope

- Any numeric threshold for how many edits are safe.
- A counter, ledger, hidden scratchpad, hook, service, file, database, or user profile used to remember how an image was produced. The freshness test is deliberately answerable without any of them.
- Any promise about behavior after the relevant conversation history is no longer available, beyond defaulting to regeneration.
- Image-quality scoring, no-reference quality metrics, noise detection, artifact classifiers, or any automated degradation measurement.
- Denoising, restoration, upscaling, or post-export processing.
- Prompt-based cleanup instructions as a repair mechanism.
- A new domain term, glossary entry, or ADR.
- A new module, agent, workflow stage, gate, or user-visible control.
- Changing which recovery paths exist, or removing the surgical edit.
- Relaxing the existing single-automatic-correction bound, or adding retries. Counting that bound per visible result under review rather than per request is a clarification of an ambiguous scope, not a relaxation; see Further Notes.
- Model parameters, API integration, or controls the active generation surface does not expose.
- Medium-specific behavior. This specification applies identically to photographic and non-photographic work.
- Batch generation and multi-panel sheets, which are specified separately.

## Further Notes

- An earlier draft of this specification proposed tracking how many image-input generations the current working image had been through. That was wrong for this codebase. The freshness-contract-reliability work already established that the skill compares only against history still available in the current conversation, promises nothing beyond it, and adds no storage to simulate a stronger promise; the coordinating workflow separately forbids a read-state tracker, and the architecture notes list persistent option history and read-state trackers among the things not to add without real failure evidence. The freshly-generated test replaces the count because it is answerable from the immediate exchange, and its uncertainty default is the safe direction.
- The bound on the automatic correction counts one correction per visible result under review, not one per request. The original wording was written when a request produced a single image, so the two readings could not be told apart and neither was chosen. The two-stage drawn-character work specified separately produces a Character Sheet plus several applications in one request, which forces the question: on a per-request reading, a Character Sheet that consumes the correction leaves every later application unrepairable, and that specification requires a failing application to be regenerated automatically. Counting per result keeps the bound doing the work it was written for — one repair attempt per image, never a retry loop on the same image — so this is a clarification of an ambiguous scope rather than the relaxation that the Out of Scope list rules out. A correction already spent on a different result does not consume this result's one attempt, and no counter or record is needed to apply it, since the bound is still answerable from the immediate exchange.
- An earlier wording defined a freshly generated result as one produced directly from the Primary Identity Anchor. That phrase was ambiguous in a way that mattered. The surgical edit row already passes the Primary Identity Anchor alongside the result being edited, so on a membership reading the product of an edit would itself be freshly generated and eligible for another edit, and the restriction would constrain nothing at all. Stating the test as a property of the image inputs closes that reading without changing what the rule was meant to do. The ambiguity surfaced through the two-stage drawn-character work specified separately, whose application images take a generated artifact as an input while also carrying the Primary Identity Anchor; the fix belongs here rather than there, because nothing about it is medium-specific.
- The quantitative findings — visible noise at roughly five to ten steps, simplification by the second step, instruction-following collapse in later steps — come from a replication study whose primary model was not the one this skill uses, and which deliberately excluded photorealistic faces from its starting images. The mechanism is well supported and was reproduced across several models; the specific step numbers are not transferable, which is why this specification contains none.
- A separate artifact affects the active model independently of the edit chain, reported widely at launch as a tiling or grime texture. A baseline form can appear on the very first image in a clean session. An amplification form, in which consecutive generations in one session grew progressively worse, eased shortly after launch, and an earlier draft of this specification recorded that as a probable fix. A re-check on 2026-08-12 found the easing was narrower than first reported: the community maintainer stated at the time that only image carryover had been corrected, the issue list still carries a residual amplification entry, no official fix has been announced, and the latest named-engineer signal, dated 2026-08-06, is that the noise is still being worked on and still visible in the wild. Treat it as an open, time-stamped condition rather than as resolved or as a permanent defect.
- Nothing in that re-check licenses extrapolating from eased same-session amplification to a clean editing chain, which is the case this specification governs. Forum testing that drove results back through the editing endpoint reproduced the artifacts either way, and that test was not repeated during the re-check.
- That artifact is strongest on high-frequency micro-structure such as glass, rock, sand, fabric weave, and hair, and weakest on flat artificial surfaces and uniform backgrounds. It is worth knowing when weighing rendering choices, but it is not an edit-chain concern and adds no rule here.
- Forum testing found the noise follows image inputs rather than stateful sessions: driving results back through the editing endpoint reproduced the same artifacts as an ordinary chat session. Switching interfaces therefore does not help; only avoiding generated results as inputs does.
- Naming an artist or school in the prompt reportedly worsens artifacts, because reference lookup pulls retrieved images into the generation context. This supports the repository's existing rule to describe style through visible anchors rather than style labels; that rule already exists and needs no change.
- Edits tend to crop in order to align output to a supported resolution bucket. This mainly threatens sets of images that must share dimensions, which is a concern for the batch specification rather than this one.
- A cleanup prompt that asks to remove noise while keeping the lines has a single third-party report of occasional success, which conflicts with the published finding that explicit denoising instructions are ineffective. Given the conflict, it is not adopted.
- Research backing this specification is in `.scratch/anime-stylized-identity/research.md`. Although that research was gathered for drawn-character work, the degradation findings are medium-independent and apply to existing photographic workflows unchanged.
