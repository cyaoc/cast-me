# Anchor drawn characters to a locked Character Sheet

When a request explicitly needs a reusable drawn character or at least two images of the same drawn character, CastMe uses two stages. One Character Sheet locks the drawn proportions, face construction, hair, eye rendering, wardrobe, palette and colour logic, line and shading treatment, and texture. Every later image of that character is generated from the sheet together with the Primary Identity Anchor, both supplied as actual image inputs. Applications branch from the sheet and never take another application as an input.

CastMe does not generate each drawn image directly from the person reference with a repeated list of features to preserve. That is the current behavior, and it cannot hold a character across images, because consistency of a recurring character across separate generations is a documented model limitation rather than a prompting shortfall. Generating each image from the previous one would hold the character but would push every additional image further along the editing chain, eroding the small marks that carry recognition once deformation flattens body differences. The two-stage flow spends one extra generation once and keeps every delivered image two steps from the user's photograph however many images are produced.

The second step is what the drawn medium pays for that. A photographic result is generated from the person's photograph alone, so a proportionate local repair costs one round trip and the recovery rules permit one. An application carries the sheet as a generated image input, so it already holds a round trip before anything is repaired, and editing it would be the drawn equivalent of editing an edit. Failing applications are therefore regenerated from the sheet and the anchor rather than surgically edited, and the automatic correction never edits one on its own initiative. The same reasoning is stricter on the sheet itself, which the freshly-generated test would otherwise admit: it is the one artifact everything downstream is built from, so a repair made to it is inherited by every image in the set instead of being confined to the one image that failed. The sheet is regenerated too. A user who asks for a local fix to an application anyway still gets one; only the skill's own initiative over that application is constrained.
